# 地图路线交付与验收要求

日期：2026-10-25。状态：用户目标与后续验收要求；不是地图已完成报告。

## 用户原话与目标

“我想要最后生成地图具体路线，不是以文字形式说明，记得我的目标是一等奖，不要做的太简单。”

以争取省一等奖为项目目标，按根目录比赛资料积累真实功能、工程、体验与过程证据，不承诺奖项或虚构评委偏好。用户需要以可交互地图展示实际道路的旅行方案，文字补充活动、费用和解释，不能以文本列表代替地图交付。

## 当前事实

按开发进度与05B报告，目前正式UI和受控接线已实现、替身验证已执行。真实地点查询2次，第2次失败后停止；模型、道路、SDK均未执行，地图与列表真实联动未验收。地图渲染代码存在不等于真实地图交付。停止与调用记录继续保留；本需求更新不自动解除停止、续期授权或重置费用。

## 05B接下来应交付的用户体验

- 当前正式工作台中显示高德实际底图，实际道路几何来自允许使用的高德响应。单独地图演示只能作中间验证。
- 每日显示已成功查询的路段、地点与出行顺序；当天集合点、去程与返程表达明确。未知路段标为缺失，不能跨缺口直线连接。
- 步行与公交地铁有图例和可辨识样式，不能只依赖颜色。可取得的交通方式、距离与估计时长随选中路段展示；未知项不填0。
- 地点顺序在地图上直接可见，不能只把序号写在鼠标悬停标题中。点击活动定位并突出地图地点；点击地图地点定位活动；切日清除上一日覆盖物。
- 地图有缩放与适配当天路线能力；手机中地图和活动/核查能方便切换。保留必要服务商标识，不用大块装饰压缩地图可操作空间。
- 显示草案、时间/个人全程费用/逐日步行核查及公共资料缺口。地图路段查到不等于预约、开放和整体旅行可行。
- 改需求后旧地图及草案明确失效。刷新、切日、缩放、活动定位不得隐式重新规划；SDK正常资源请求与业务请求分别记录。

## 实施次序

1. 优先核对地点查询输入合同与错误分类。纯检索字段和“待核实”等备注分离；名称搜索、POI详情、地理编码按核查后的官方接口用途选择，不将机构地址匹配直接当入口匹配。不得把尚未保留诊断的旧失败认定为某一根因，不暗中自动改接口重试。
2. 使用已知合成响应完成针对性验证，提出一次具体恢复计划：查询对象、接口、最大次数、道路方式、SDK条件、停止规则及额度承接。当前已发生次数与费用预留不得清零。用户决定恢复范围后才执行真实请求。
3. 东门集合点至迎泽公园北门可作为首条建议测试段；它是中间验收点，不是替代完整行程的最终产品。查询后仍核对落点，地图位置确认与未来日期通行确认分别记录。
4. 首段真实地图和列表联动通过后，接通模型草案及每日路线。四候选与午餐等缺口继续保留，不靠补造地点填满两天。
5. 提供实际运行截图和操作录屏、独立结果记录；如失败，说明失败位置和后续选择，不以测试数量代替用户可见交付。

## 后续完整产品要求

05B之后继续实现真实多Agent交接及事件看板、锁定活动、条件变化重排、前后方案对比与保存/导出。核心案例为锁定第2天午餐，再将当天步行上限由6公里降到4公里；旧新方案的路线、活动与核查变化可检查。单次模型生成不能称为多Agent，动态节点必须来自实际执行事件。

本轮先推进真实地图主流程；不为显得复杂添加无作用模型角色、装饰动画或新城市。
