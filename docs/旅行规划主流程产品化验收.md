地图与当天活动双栏，四角色横排在上方。节点展示实际产出和交给下一角色的内容，点击进入侧栏；程序核算独立标示，不算第五个模型角色。技术JSON和调用记录保留折叠入口。手机通过地图/活动/协作切换。

现有八处测试位置与两家午餐直接复用。本轮真实调用没有地点检索。缺失已知地点时服务端固定太原检索：本页完整且唯一精确的街区/广场候选可自动作为测试落点；博物院集合、院门与主馆入口不能用机构中心替代，只有此类入口不清、同名、查询失败才显示候选处理入口。结果带来源与取得时间，不将测试落点升为官方入口。不是任意城市或任意新增活动规划器。

午餐作为活动卡，展开依据、换店和锁定时间；已锁本餐换店前须明确解锁。直接锁定本餐不连带改步行限制；08原有“第2天4公里”场景仍保留。当前支持一项午餐锁定，不能静默替换另一餐。没有可信候选明确报缺口。

## 四角色如何影响首次生成

1. 需求协调独立请求：逐人偏好、预算、逐日步行、时间和锁定，输出硬约束及协调摘要。
2. 方案筛选独立请求：真实使用协调输出及指纹，在已有来源的地点/餐饮候选中选择顺序、午餐，解释逐人匹配。当前首日博物院/公园组合固定，第二日比较两种街区顺序，范围有限。
3. 程序先按筛选顺序取得道路；行程规划独立请求实际收到这些道路预测，提交逐项停留分钟及依据。程序按筛选顺序编译草案，不让模型补造坐标、票价或营业事实。
4. 程序重新算时间、逐人费用和逐日步行并应用锁定；行程审查独立请求实际使用规划输出和核算结论，最多一次回交。全轮最多6次模型、24次道路工具尝试、12分钟，模型单次60秒、并发1，无业务自动重试。

采用和拒绝仍由用户决定；超出已计入上界、锁定冲突或道路过期禁止采用。失败保留采用结构；修改需求使旧运行/预览失效。只保存自有结构和选择，不保存道路几何；导出白名单不扩大。

- 第一次真实规划缺少内层plan.version，合同拒绝，3模型/14道路/1SDK；未调用审查。
- 第二次规划返回语法错误JSON，3模型/14道路/1SDK；未修补输出。改为小型stays合同，由程序编译已选顺序，实际模型仍决定停留。
- 第三次4模型/14道路/1SDK完成四角色，保留冲突。
- 发布复验遇Windows EPERM账本替换失败，2模型/3道路/1SDK后结束。加入最多6次短时本地原子替换尝试；绝不重发业务请求；持久失败有清楚错误。
- 再次发布4模型/14道路/1SDK通过。另修复地图子页说明挤占手机底图、对比说明挤占活动首部、采用失败回滚、选择存档只保存points/mode/meals而非route。
