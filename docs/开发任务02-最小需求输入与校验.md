# 开发任务 02：最小需求输入、结构校验与保存恢复

整理日期：2026-10-24。状态：交接建议，待开发聊天执行。由 AI 根据用户已确认的需求及实际文件整理，不是用户独立撰写的原始提示词，也不是完成证明。

## 本轮目标

实现一个可实际运行、可由用户体验的最小需求入口：输入旅行条件 → 程序检查 → 显示整理结果及待补资料 → 本地保存与恢复。用户应能看见每个人的偏好与限制被分别保留。此轮不要求生成行程，不做多 Agent 看板或地图展示。

## 必须带入的产品需求

- 目的地区域山西，每次一座城市，人数 1～6、天数 1～3 可选；目前仅太原有候选资料。界面只将太原标为可测试，不虚设其他可用城市。后续加城市时可扩展数据。
- 每位同行者有稳定标识、匿名显示名、独立偏好、个人总预算、按天的步行上限；人数与成员数量一致。具体字段组织方式可由开发合理确定。
- 以已确认案例预填：太原、3 人、2026-11-07/08、每天 09:00～18:00；三人分别喜欢历史展览、风景拍照、美食少走路。
- 每人两天预算 600 元，包含餐饮/门票/市内交通，不含住宿及往返太原大交通；不得用总额平均覆盖个人上限。
- 两天起终点均为山西博物院东门外公共集合点；采用名称与已有地址线索，不捏造坐标，不把它写成酒店。保留落点未人工核对标识。
- 每人每天总步行上限 6 公里，包含接驳和内部步行。单位明确。
- 未来重排规则是用户锁定第二天午餐后改为 4 公里；当前没有午餐活动，不创建虚假锁定项，不提前改动初始 6 公里。

## 实施边界

1. 选择一个适合后续扩展、能在本机运行的轻量方案并简述理由，勿让用户从大量框架中选择。复用已有工具，不引入无关服务、账号或数据库。不要求已有 JS 地图 Key。
2. 提供简洁的本地交互页面，允许修改人数、连续日期/天数、成员偏好、预算和步行上限，查看结构化需求摘要。首次页面明确是“需求准备”，不显示生成成功或行程可行。
3. 程序验证类型、必填、支持城市、人数/成员一致、1～3 个连续日期、每日起止时间有效、金额与距离非负且有限、成员标识唯一。拒绝布尔冒充数字、空值自动变零等情况。失败返回中文字段提示并保留用户输入，不自动放宽条件。
4. 日期与天数只能有一个明确的计算来源，避免互相矛盾。人数减少时若涉及已填写成员，避免无提示丢失其资料。匿名需求即可，不收身份证、联系方式或真实住宿。
5. 保存恢复只涉及用户输入和本应用自有状态，包含格式版本；不保存服务商坐标、路线或未经许可的地图响应。明确存储在当前浏览器还是本地文件，刷新/重新打开可恢复，损坏或不兼容的数据不能静默覆盖。
6. 显示“输入检查通过”和“旅行可行性未验证”的区别；列出当前仍待核实的入口、未来日期营业预约、具体午餐、交通及内部步行。接口成功的历史记录不能代替这些数据。
7. 如用固定样例，明示“固定测试需求”；无需模型就能实现的表单校验由程序完成，不展示虚假 Agent 运行。

## 验收

- 默认案例可显示三人独立要求、两个日期、费用包含范围、每天时段及起终点，不能缩写丢失关键限制。
- 实际验证 1 人/1 天和 6 人/3 天的有效输入；拒绝 0/7 人、0/4 天、成员数不符、非连续日期、结束早于开始、非法数字及重复成员标识。
- 改某人的预算或偏好后，其他人原值不被误改；保存后刷新恢复一致。损坏存档有可理解提示，保留恢复前输入。
- 页面或摘要不能在资料缺失时声称预算、营业窗口、6/4 公里或完整路线已校验。
- 自动化检查覆盖关键校验与保存恢复行为；实际启动并体验默认案例，报告浏览器验证通过/失败/未验证，不用仅构建通过替代交互验证。
- 本轮实际地图与模型新请求为 0；不改动首次真实验证记录来冒充新测试。
